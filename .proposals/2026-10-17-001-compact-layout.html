方案 003 · UI 紧凑化 —— 为更大字号腾空间

2026-10-17 · 需求原话「我想让UI更紧凑一些来保证字体更大」 · 依据：CDP 真实渲染实测 · 状态：等待批准

问题的算术

设计窗高 = 非名单区(chrome 260px) + 名单区(3 × 行高)，而 行高 = 53.4 × 字号系数。

所以：chrome 越厚，同一块屏幕上能容纳的字号就越小。你想让字更大 —— 直接拉高系数会把窗口顶到屏幕外， 而 chrome 里恰恰有 ~90px 是「空气」：不是名单区，也不是内容，纯留白与内边距。

另有免费的 +15%：压缩后设计窗高变小，若你的窗口比设计窗高更高， 等比缩放会把余高用掉（zoom 上限 1.15），字号随之再变大 —— 不需要额外设置。

横向：一块被浪费的宽度（可选）

窗口 800px 宽，但窗框 max-width: 576，两侧还各留 32px 舞台内边距 —— 实际只用了 72% 的宽度。

横向改动只影响「长名字是否缩档」，对短名字没有视觉变化；不改动名单区高度，也不影响任何动画几何。

设计意图：不是乱压，是换成统一节奏

  • 现状间距是 6/8/10/13/14/16/18/22/26/32 的混合；紧凑版统一到 4px 基准阶梯（4/8/12/16/20），比例关系保持一致。
  • 保留全部设计语言：雾玻璃窗框、虚线分隔、金色高亮、圆角比例（24 → 20 与更薄的内边距成比例）。
  • 抽取按钮依旧是唯一的实心光块 —— 先减内边距、后减字号，保住主按钮的存在感。
  • 图标钮 34px 对鼠标足够（Windows 桌面建议 32px+），不套用 44px 触控基准。
  • 名单区 3 行视口从不压缩：省下的每一像素都还给字号。

风险与回滚

风险影响处置
门禁断言连锁失效npm test / verify 脚本变红档位确定后先改 4 个脚本再跑；这是本方案最容易出问题的地方
视觉过挤「紧凑」变成「憋屈」分三档让你选；中度只收到 4px 阶梯，未触及极限
顶栏钮变小点击目标变窄34px 仍高于桌面建议下限；不喜欢就退回 36px
状态提示字号 15 → 13px可读性下降目检确认；提示文字本就短（「可抽 47 人」）
minHeight 与新设计窗高不一致小字号下窗口偏高、底部空一块同步改 minHeight；改完实测各档窗高
宽度不变量被破坏名单区宽度塌缩（历史回归）窗框 max-width 始终 = 视口 max-width + 2×窗框内边距，注释同步
回滚：改动只涉及样式与几何常量，不写 settings.json、不动数据文件。 分支未合并时 git branch -D；已合并则 git revert。

需要你定的四件事

决策选项（粗体为我的建议）
① 紧凑力度 中度（chrome 260→170，省 90px） · 轻度（→200，稳） · 激进（→135，很密） · 或按上表自由混搭
② 要不要同时抬高字号上限 要，2.5× → 3.0×（中度下 3.0× 窗高 650px，比现在 2.5× 的 662px 还矮） · 保持 2.5× 只做紧凑 · 抬到 3.2×
③ 横向也用起来吗 用（舞台左右 32→20、视口 560→600） · 不动，只做纵向紧凑
④ 分支归宿 先目检并合并品牌文案分支，再从 master 拉 feat/compact-layout · 直接叠加为第 3 个提交（一次合并）
提醒：「紧凑化」会改变窗口的默认高度（中度下 1.0× 时 500 → 410）。 如果你更希望「窗口高度不变、只把字变大」，说一声 —— 那就走②抬上限、不动 chrome 的路线，收益会小一些。
