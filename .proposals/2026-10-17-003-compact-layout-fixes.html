① 目标与背景

你的要求：把「003 代码审查」里的修复项全部修掉。

背景：feat/compact-layout 把默认窗高从 500px 压到 375px，并新增「字体大小」字段，但没有同步处理设置面板的高度。结果：默认状态下面板上下各被裁约 68px——「设置」标题完全看不到，「关闭」按钮也不可见。

面板高度 511px
设计窗高 375px
溢出 136px
不可达控件 2 个（标题、关闭）

为什么必须修

  • 设置面板是「字体大小」功能的唯一入口，面板被裁直接影响本轮新功能可用性。
  • 面板最窄情况下（最小窗口 640，zoom≈0.8）同样溢出，问题跨窗口尺寸存在。
  • 在待批准的 002-窄窗口 方案里，1.75× 设计窗高为 414px，仍小于 511px——不修这条，002 落地后依然是坏的。
已量化：面板 511px（h2 41 + 字段 66/66/45/121 + 关闭钮 40 + 内边距 44 + 边框 2）。仅靠压缩间距无法降到 375px 以内（需减约 136px），因此必须让面板可滚动，而不是继续挤压留白。

② 技术选型与架构设计

必修项：让设置面板在超高时可滚动

采用的 CSS（已在真实 Chrome 注入预验证，见下表实测）：

/* src/style.css */
.overlay {
  position: fixed;
  inset: 0;
  background: var(--overlay-bg);
  display: flex;
+ overflow-y: auto;            /* 内容高于视口时可滚动 */
+ padding: 12px 0;             /* 贴边留呼吸，滚动时首尾都能看全 */
- align-items: center;
+ align-items: flex-start;     /* 超高时从顶部开始，两端都可滚到 */
- justify-content: center;
+ justify-content: flex-start;
  z-index: 10;
}
.overlay[hidden] { display: none; }   /* 保留，勿动 */

.panel {
  ...
+ margin: auto;                /* 能放下时居中；放不下时两端都可滚到 */
}
为什么不用 align-items:center + overflow：这是经典的 flex 居中陷阱——子元素比容器高时，居中会把「上溢」的部分推到滚动区之外，顶部永远滚不到。改用子元素 margin:auto 后，能放下时仍居中，放不下时自动退化为「顶部对齐 + 可滚到底」，两端都可达。

配套：把两条几何不变量写进门禁

这次必修项能漏到审查阶段，根因是 verify-render.js 没有覆盖它们。新增两条断言：

注入 800×设计窗高
→
断言 innerH − 视口高 = 135（DESIGN_CHROME_H）
→
打开设置面板
→

面板可达性的断言写法（避免把「面板必须 ≤ 视口」写死，因为滚动是可接受解）：

// 面板顶端可达 && 关闭按钮可达
const reachable =
  (panelTop >= 0 || scrollable) && closeBtnBottom <= innerHeight + 1;

建议项 1：加载设置期间的字号补丁不再被丢弃

根因是 input 处理器只记了补丁、没有 bump settingsRevision，导致 changedDuringLoad 恒为 false，补丁在 loadAndApplySettings 中被丢弃。

// src/main.js 字号 input 处理器
fontScaleInput.addEventListener("input", () => {
  const s = setFontScale(fontScaleInput.value);
-  if (settingsLoadPatches) settingsLoadPatches.fontScale = s;
+  if (settingsLoadPatches) {
+    settingsLoadPatches.fontScale = s;
+    settingsRevision += 1;   // 与 applyTheme/applyScheme 同机制：让「加载期用户操作」生效
+  }
});

建议项 2：保存失败时仍完成窗口适配

// src/main.js 字号 change 处理器
  handleSettingAction(async () => {
-   await saveCurrentSettings({ fontScale: currentSettings.fontScale });
-   await fitWindowHeight();
-   applyLayoutScale();
+   try {
+     await saveCurrentSettings({ fontScale: currentSettings.fontScale });
+   } finally {
+     // 保存失败也要保证窗口高度与缩放与新字号一致（失败仍向上抛，状态照常提示）
+     await fitWindowHeight();
+     applyLayoutScale();
+   }
  })

⑥ 参考项里我建议不修的 3 条（请你裁决）

你要求「修复项全部修复」。以下 3 条我判断不宜在本轮做，理由如下；若你仍要求做，请在批准时说明，我照做。

1 applyRowFonts 拖动时的性能 —— 建议另开一轮

实测（真实 Chrome，42 行填满，连续 20 次 input）：

单次总耗时 3.08ms
单次峰值 4~6ms
帧预算 16.7ms

即每次拖动约占一帧的 20%~35%，桌面端可接受。而两种改法都有代价：

  • rAF 合并：会让「拖动即改 CSS 变量」变成「下一帧才改」。现有 4 处断言（3 个脚本 + 单测）都是同步校验变量值，全部要改成异步等待——改动面反而大于问题本身。
  • 只重排可见行：需从 slotList 位移反推可见行区间；且 finish() 只重排命中行，静止时相邻两行可能残留旧档位 → 引入新的视觉缺陷。

结论：维持现状，并把实测数字写进 main.js 注释备查。若将来在小屏/低端机上感到卡顿，再单独立项（届时同步把 4 处断言改为异步）。

2 fitWindowHeight 的 taller 判断 —— 建议维持 + 补注释

它只会在「启动」与「改字号」两个时机被调用，不会在用户拖拽窗口时打扰用户。若用户手动把窗口压得比设计窗高更低，applyLayoutScale 的 zoom 会等比缩小整个界面，内容本来就装得下。维持现状，仅补一句注释说明「非持续干预」。

3 屏幕高度钳制（3.2× 时窗高 648px）—— 建议不做

给窗口加高加「不超过屏幕工作区」的钳制属于新功能（要读显示器尺寸、要定义超出时的降级策略），超出本次审查范围。且 3.2× 是用户主动选择的极端档位。建议仅在本方案里记录，不实现。

需要在批准时确认的 2 个点：
  1. 上面 3 条是否同意「本轮不做」。
  2. 阶段 5 是否要重建便携版并替换桌面 exe（前端改动需重建才生效）。
